# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is the **device tree** for the Motorola Edge 30 Fusion (codename `tundra`), a Qualcomm SM8350 "lahaina" platform device. It is meant to live at `device/motorola/tundra/` inside a full Android/PixelOS source tree (repo-synced via `.repo/manifest.xml` at the tree root) — it is **not buildable standalone**. There is no local SDK, no `gradlew`, and no unit test suite; "building" means lunching this device inside a full ROM source tree.

The repo builds `custom_tundra` (`custom_tundra.mk`), inheriting:
- `device/motorola/tundra/device.mk` (this repo — hardware feature packages, PRODUCT_COPY_FILES, HAL/HIDL/AIDL services)
- `vendor/custom/config/common_full_phone.mk` (PixelOS common config, lives in a sibling `vendor/custom` repo)
- `vendor/motorola/tundra/tundra-vendor.mk` and `BoardConfigVendor.mk` (proprietary blobs, in a sibling `vendor/motorola/tundra` repo generated by the extraction scripts below)

Companion repos referenced but not present here: `kernel/motorola/tundra`, `hardware/motorola`, `vendor/motorola/tundra`, `vendor/custom`.

## Common commands

These only work from the root of a full source tree with this repo synced at `device/motorola/tundra`.

```bash
# Set up environment and pull in vendor proprietary blobs (run from device/motorola/tundra)
./proprietary-setup/extract-files.py

# Regenerate proprietary-files.txt / makefiles from a connected device or dump
./proprietary-setup/extract-files.py --regenerate_makefiles

# From tree root: initialize and build
source build/envsetup.sh
lunch custom_tundra-userdebug   # or -user / -eng
mka bacon                        # or `m` for a plain build
```

`extract-files.py` requires `tools/extract-utils` (LineageOS `extract_utils` Python package) to be present in the source tree at `../../../../tools/extract-utils` relative to this dir — the shebang line in `extract-files.py` sets `PYTHONPATH` accordingly.

There are no lint/format/test commands specific to this repo — changes are validated by doing a full device build (`mka bacon`) and flashing/booting.

## Architecture

This is primarily a collection of Android build-system fragments (`.mk`, `Android.bp`), config/XML blobs, init scripts, sepolicy, and RRO overlays — not application code. Key areas:

- **`device.mk`** — the main product definition. Organized into commented sections (Audio, Bluetooth, Camera, Display, Fingerprint, GPS, NFC, RIL, Sensors, Telephony, USB, Vibrator, WiFi, etc.), each adding `PRODUCT_PACKAGES` and `PRODUCT_COPY_FILES` for that subsystem. When adding/removing a HAL or vendor package, find and edit the matching section rather than appending elsewhere.
- **`BoardConfig.mk`** — low-level board/kernel/partition config: CPU arch (`arm64`, `cortex-a76`/`armv8-2a-dotprod` primary, `armv8-a` 32-bit secondary), A/B partition layout, AVB/verified boot, recovery, sepolicy includes, WiFi driver config. Pulls in `vendor/motorola/tundra/BoardConfigVendor.mk` partway through.
- **`hardware/`** — device-specific native HAL implementations built via Soong (`Android.bp`), currently `fingerprint` (biometrics HIDL service + `libudfps_extension` for under-display fingerprint/SurfaceFlinger integration) and `gps` (a large vendor GNSS/location stack: `core`, `gnss`, `geofence`, `batching`, `location`, `utils` sub-libraries) and `sepolicy` (vendor/public/private `.te` policy + contexts).
- **`rro_overlays/`** — Runtime Resource Overlay packages (`FrameworksResOverlay`, `SettingsOverlay`, `SettingsProviderOverlay`, `SystemUIOverlay`, `TelephonyOverlay`, `WifiOverlay`). Each is a standalone `runtime_resource_overlay` Soong module with its own `AndroidManifest.xml` + `res/`. `device.mk` sets `PRODUCT_ENFORCE_RRO_TARGETS := *`, so target-package resource changes for this device generally belong in these overlays, not in framework source.
- **`configs/`** — static config/XML payloads copied into `/vendor` via `PRODUCT_COPY_FILES` in `device.mk`: audio (mixer paths, policy, effects), wifi (WCNSS, supplicant overlays), media codecs, keylayout, HIDL manifest/compatibility matrix, task profiles.
- **`props/`** — `odm.prop`, `system.prop`, `vendor.prop`, wired in via `TARGET_*_PROP` in `BoardConfig.mk`.
- **`rootdir/`** — `init.*.rc` scripts and `bin/*.sh` shell scripts copied to `/vendor/etc/init` and `/vendor/bin` respectively (the `bin/*.sh` copy is done generically via a `$(foreach ... wildcard ...)` in `device.mk`, so new scripts dropped in `rootdir/bin/` are picked up automatically — no `device.mk` edit needed). Also holds `fstab.qcom` (referenced from both vendor and recovery/vendor_boot ramdisk) and `ueventd.rc`.
- **`proprietary-setup/`** — `extract-files.py`/`setup-makefiles.py` (LineageOS `extract-utils`-based blob extraction), `proprietary-files*.txt` / `proprietary-firmware.txt` blob lists, and `ims-patches/` (source patches applied to Motorola's IMS stack for AOSP compatibility).

## Conventions

- Commit messages are prefixed `tundra: ` followed by an imperative summary (e.g. `tundra: Fix slo-mo and normal cam corder for moto camera`), consistent with LineageOS/AOSP device-tree conventions. Occasionally a scoped prefix is used instead, e.g. `tundra: rro_overlay: Update pixel pitch` or `tundra: audio: increase TX decoder mic gains (84 -> 104)`.
- License headers: files use `SPDX-License-Identifier: Apache-2.0`, generally under "The AwakenOS Project" or "Paranoid Android" copyright per historical origin of the file — match the header style already present in a file's directory rather than introducing a new one.
- HAL/service packages added to `device.mk` should be grouped under the existing subsystem comment heading; keep `PRODUCT_PACKAGES` / `PRODUCT_COPY_FILES` blocks alphabetized within their existing groupings where the surrounding code already does so.
